در ادامه، نسخه به‌روزرسانی‌شده و کامل‌تری از پرامپت (سند نیازمندی) را ارائه می‌کنم که تمام موارد جدید شما را نیز پوشش می‌دهد. زبان سند فارسی است تا بتوانید مستقیماً به تیم فنی ارائه دهید.

# سند نیازمندی‌های سامانه مدلسازی معماری مبتنی بر Arcadia (نسخه بومی)

## ۰. معرفی کلی و اهداف

ما قصد داریم یک ابزار **وبی** برای مدلسازی معماری سیستم‌ها با متدولوژی **Arcadia** ایجاد کنیم. این ابزار نسخه‌ای بومی‌سازی‌شده و کاملاً بازطراحی‌شده از نرم‌افزار متن‌باز Capella است با این تفاوت‌های اساسی:

- به‌جای Eclipse RCP، یک **برنامه تحت وب** مدرن و واکنش‌گرا است.
- مشکلات پیچیدگی UI/UX نرم‌افزار Capella را برطرف می‌کند و تجربه‌ای روان و بدون دغدغه برای معماران فراهم می‌آورد.
- امکان **مدیریت همزمان چند پروژه** و **چند مدل** در هر پروژه را می‌دهد.
- قابلیت **خروجی‌گیری (دانلود)** مدل‌های کامل برای استفاده در ابزارهای دیگر را دارد.
- دارای سیستم **مالکیت و سطوح دسترسی** (Owner, Editor, Viewer) برای کاربران ثبت‌نام‌شده است.
- موتور **اعتبارسنجی کاملاً منطبق با قوانین Arcadia** دارد که اشتباهات متداول را شناسایی و از ایجاد آنها جلوگیری می‌کند.
- باید بتواند مدل مرجع پیچیده **In-Flight Entertainment (IFE)** را به‌عنوان معیار پذیرش، بدون نقص مدل‌سازی و بازآفرینی کند.

## ۱. پشته فناوری پیشنهادی (Tech Stack)

برای پیاده‌سازی از ترکیب فناوری‌های زیر استفاده شود:

| لایه | فناوری |
|------|--------|
| Frontend Framework | **Next.js 15 (App Router)** + React 19 |
| Language | **TypeScript** (strict mode) |
| UI Components | **Shadcn/ui (latest)** |
| Styling | **Tailwind CSS v4** |
| Diagram Rendering | **React Flow** (پیشنهادی) یا یک کتابخانه منعطف شبیه به آن که امکان طراحی گره‌ها و یال‌های سفارشی و تعاملی را در سطح بالا فراهم کند. |
| State Management (Client) | **Zustand** |
| Server State & API Calls | **TanStack React Query** |
| Architecture Pattern | **Clean Architecture** + **Domain-Driven Design (DDD)** |
| Validation Engine | پیاده‌سازی یک Domain Service داخلی برای بررسی قوانین Arcadia |

## ۲. معماری کلی سیستم (Clean Architecture & DDD)

- **لایه Domain:** شامل Entityها، Value Objectها، Aggregateها و Repository Interfaces برای مفاهیم اصلی مثل `Project`، `Model`، `Diagram`، `Element` (Operational Entity, Component, Function و ...) و مجموعه `ValidationRule`.
- **لایه Application:** Use Caseها مانند "ایجاد پروژه"، "ایجاد مدل"، "افزودن عنصر به دیاگرام"، "اعمال Rule Set"، "خروجی‌گیری مدل"، "مدیریت دسترسی".
- **لایه Infrastructure:** پیاده‌سازی Repositoryها با پایگاه داده (PostgreSQL یا MongoDB)، سرویس‌های ذخیره‌سازی فایل، پروایدرهای هویتی (Auth).
- **لایه Presentation:** صفحات و کامپوننت‌های Next.js با استفاده از Zustand برای State محلی دیاگرام و TanStack Query برای واکشی داده‌های پروژه.

## ۳. ویژگی‌های کلیدی

### ۳.۱ مدیریت چندپروژه‌ای و چندمدلی
- کاربر وارد Workspace خود می‌شود.
- در Workspace می‌تواند **پروژه‌های** مختلف ایجاد کند.  
- هر پروژه دارای **چندین مدل** (Model) است.  
  مثال: یک پروژه «IFE System» شامل مدل‌های «IFE Operational Analysis»، «IFE System Analysis» و ... می‌شود.
- مدل‌ها کاملاً ایزوله هستند و هرکدام می‌توانند شامل چندین دیاگرام از نماهای گوناگون باشند.

### ۳.۲ دسترسی و سطوح کاربری
- **ثبت‌نام و احراز هویت:** با ایمیل/رمز عبور یا OAuth.
- هنگام ایجاد **مدل**، ایجادکننده به‌طور خودکار **Owner** می‌شود.
- Owner اختیارات کامل دارد و می‌تواند سایر کاربران ثبت‌نام‌شده را با نقش‌های زیر به مدل دعوت کند:
  - **Editor:** قابلیت ویرایش و اعمال تغییرات در مدل.
  - **Viewer:** فقط امکان مشاهده و بازرسی مدل، بدون حق تغییر.
- این سیستم دسترسی مبتنی بر مدل (Model-level) است؛ می‌توان پروژه‌ها را نیز با سیستم دسترسی مشابه مدیریت کرد.

### ۳.۳ دانلود و خروجی‌گیری مدل
- کاربر Owner یا Editor بتواند مدل کامل (شامل تمام المان‌ها، دیاگرام‌ها و ارتباطات میان‌نما) را در یک قالب استاندارد **قابل تبادل** دانلود کند.
- فرمت پیشنهادی: **ساختار JSON اختصاصی** که قابل تبدیل به استانداردهای دیگر (مثل XMI یا قالب مبادله Capella) باشد. حداقل، یک JSON قابل خواندن که کل نمودار و واقعیت‌سازی‌ها را ذخیره کند.
- در صورت نیاز، امکان وارد کردن مجدد این فایل نیز فراهم شود.

### ۳.۴ تجربه کاربری (حل مشکلات Capella)
رابط کاربری باید کاملاً بازاندیشی شده و از پیچیدگی‌های Eclipse RCP رها باشد:
- **ویرایشگر دیاگرام** مبتنی بر React Flow: کشیدن و رها کردن عناصر از پالت، اتصال با خطوط هوشمند.
- **پالت زمینه‌گرا:** بسته به نوع دیاگرام، فقط عناصر مجاز همان نما نمایش داده شود.
- **ممیزی خودکار:** هنگام ترسیم، اگر عملی مغایر با قواعد Arcadia باشد، همان لحظه به کاربر هشدار داده شود و از ایجاد آن جلوگیری گردد.
- **مرورگر مفهومی:** یک پانل کناری که درخت کامل مدل را نشان دهد و با کلیک روی هر عنصر، تمام ردیابی‌ها (traces) و واقعیت‌سازی‌ها (realization) آن در سایر نماها برجسته شود.
- **انتقال خودکار (Transition):** قابلیت کلیک‌راست روی یک کارکرد SA و انتقال آن به نمای منطقی با حفظ پیوندها.

## ۴. نماهای Arcadia و دیاگرام‌های پشتیبانی‌شده

مانند سند قبلی، ۵ نمای اصلی را پیاده‌سازی می‌کنیم:

1. **تحلیل عملیاتی (OA)**
   - **OEBD:** نمودار موجودیت عملیاتی - قابلیت ساخت چندین OEBD هم‌زمان.
   - **OAD:** نمودار فعالیت عملیاتی.
2. **تحلیل سامانه (SA)**
   - **SAB:** دیاگرام معماری سامانه.
   - **زنجیره‌های کارکردی (Functional Chains).**
3. **معماری منطقی (LA)**
   - **LAB:** نمودار معماری منطقی.
   - **LDFD:** نمودار جریان داده منطقی.
4. **معماری فیزیکی (PA)**
   - **PAB:** نمودار معماری فیزیکی.
   - **نمودار استقرار (Deployment).**
   - پشتیبانی از مفهوم REC/RPL برای تکثیر قطعات.
5. **EPBS:** ساختار تفکیک محصول نهایی.

## ۵. موتور قوانین و اعتبارسنجی (Validation Engine)

یک سرویس Domain‑Driven جداگانه مسئول بررسی قوانین است. این سرویس باید در زمان‌های زیر فعال شود:

- هنگام اتمام رسم یک اتصال (در صورت نقص، اتصال قطع و به کاربر اخطار داده شود).
- هنگام ذخیره‌سازی مدل (فقط اجازه ذخیره مدل معتبر).

**قوانین کلیدی (مطابق Arcadia):**
- فقط **کارکردهای برگ (Leaf Functions)** می‌توانند پورت تبادل (Exchange Port) داشته باشند.
- هر کارکرد برگ باید حداقل به یک مؤلفه (Component) تخصیص یابد.
- هر رابط (Interface) باید حداقل یک Exchange Item را ارجاع دهد.
- هنگام اتصال دو کامپوننت در نمای فیزیکی، سیستم باید بررسی کند آیا **Realization Link** معتبر به عناصر منطقی متناظر وجود دارد یا خیر. اگر خیر، اتصال **مسدود** شود.
- یکتایی شناسه‌ها در محدوده مدل.

## ۶. مدل تست: In-Flight Entertainment (IFE)

برای اطمینان از صحت عملکرد، ابزار باید قادر به مدل‌سازی کامل سیستم IFE شامل تمام نماهای زیر باشد:

- **OA:** تعریف مسافران (Passenger)، خدمه (Crew)، سیستم‌های هواپیما، فعالیت «تماشای فیلم».
- **SA:** کارکردهای سیستمی مانند «مدیریت سرویس ویدئو درخواستی»، پخش اطلاعیه‌ها، زنجیره‌های کارکردی.
- **LA:** مؤلفه‌های منطقی مانند Media Server، Seat Display Unit.
- **PA:** مؤلفه‌های فیزیکی، اتصالات شبکه و تکثیر آداپتورها با REC/RPL.

این مدل باید توسط تیم توسعه به‌عنوان یک پروژه نمونه داخل ابزار پیاده‌سازی شود و تمامی قواعد اعتبارسنجی را پاس کند.

## ۷. جمع‌بندی و خروجی نهایی

پروژه باید یک اپلیکیشن وب تک‌صفحه‌ای (SPA) قابل نصب در سرور باشد با رابط کاربری کاملاً فارسی (و قابلیت تغییر زبان) که تجربه‌ای سریع، بصری و کاملاً منطبق بر متدولوژی Arcadia ارائه دهد. هدف نهایی:

> معمار بتواند بدون درگیری با پیچیدگی‌های ابزاری، هر مدل دلخواه خود (از جمله مدل IFE) را تنها با چند کلیک بسازد، میان نماهای مختلف پیمایش کند، خطاها را به‌موقع تشخیص دهد، مدل را با همکاران به اشتراک بگذارد و در نهایت خروجی استاندارد دریافت کند.
